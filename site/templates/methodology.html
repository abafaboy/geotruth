Methodology

What is measured

Every case of the corpus is a pair of geometries A and B. For each case a library is asked for as much of the following as it offers:

  • Relate: the DE-9IM intersection matrix of A and B;
  • named predicates: intersects, disjoint, touches, crosses, overlaps, contains, covers, within, covered by, equals;
  • validity of A and of B;
  • overlay: the intersection, union, difference and symmetric difference.

The semantics are the OGC Simple Features model as implemented by JTS and GEOS RelateNG and OverlayNG, with the default Mod-2 boundary node rule and the default validity rules (GEOS IsValidOp). Before anything else, each adapter must echo the operands back bit for bit (the parse-echo canary: 253+1 written as an integer, subnormals, −0.0, 0.30000000000000004, the largest double), so that no result is blamed on a library when the adapter read the input wrong.

Exact arithmetic

  • Every double is a rational number. Each coordinate is an IEEE-754 double m·2e, so every question about the input has one right answer. Inputs are read the way libraries read them: a JSON number becomes a double first.
  • Per-case scaling to integers. All coordinates of a case are multiplied by the same power of two, which turns them into integers exactly. Orientation tests, segment intersections and point location are then integer arithmetic; intersection points are kept as homogeneous integer triples, never rounded.
  • No tolerance anywhere in a decision. Quantities with square roots (distances in the overlay grading) are kept as exact surds or certified bounds.
  • The engine can abstain. A case over the engine's size or time budget is engine_skipped; an engine failure is engine_error. Neither is ever counted against a library. This site was built with engine $engine_version.

Two independent routes to the DE-9IM matrix

  • The arrangement route (DESIGN §2.3) nodes both operands into one planar subdivision, locates every vertex, edge and face in A and in B, and takes, for each pair of locations, the largest dimension of a cell there. Assertions run on every matrix: EE = 2; relate(B, A) is the transpose of relate(A, B); a non-empty areal A has a non-empty II, IB or IE.
  • The witness route (DESIGN §2.4) locates witness points directly in the original A and B with a standalone point locator: every vertex, every intersection point, the midpoint between consecutive split points of every segment, and a point strictly inside every face. It shares only the integer primitives with the arrangement route.
  • The two routes are cross-checked against each other, against the audited references in tests/reference and against GEOS on integer lattices by the test suite (tests/crosscheck). On this site, every example on a failure page is re-checked by the witness route when the site is built, and the page says whether they agree.

Overlay and its certificate

An overlay result is the closure of the cells the operation selects: A ∧ B for the intersection, A ∨ B for the union, A ∧ ¬B for the difference, A ⊕ B for the symmetric difference. There are two variants: the non-strict result (OverlayNG's default, which keeps the lines and points where boundaries touch) and the regularized areal result (polygons only, what polygon-only clippers promise). A library's output is graded against the non-strict result when it contains lines or points, and against the areal result otherwise.

The certificate (DESIGN §2.6) is the independent check of an overlay: it builds a common subdivision of A, B and the result from scratch and checks that a witness of every cell is located in the result as the operation requires. It shares nothing with the overlay builder but the integer primitives. Every overlay example on a failure page is certified when the site is built.

Controls

  • The engine control runs the exact engine behind the same adapter contract as every library. It must score 100%; anything else is a harness bug.
  • The mutant is the engine with deliberate faults. The scorer must catch them, and its row shows that it does.
  • CGAL with its exact kernel (Epeck) is an external control: an independent exact implementation whose overlays should equal the engine's regularized areal results as point sets.

Scoring

The scorer writes one record per case, library and capability. Relate is compared with the exact matrix, character for character. The named predicates of a case are graded together, as one record, so a library that derives all ten predicates from one call is not counted ten times. Validity is graded on the boolean (the reason is shown, not graded). The verdicts:

A predicate that the manifest derives from the relate matrix is marked derived when the relate answer of the same case is wrong too, and an overlay the library computes from other overlays (for example a symmetric difference from two differences) is marked derived when one of those is wrong: a fault is counted once.

Overlay tiers

Overlay output cannot always be exact: the exact result can have vertices that are not doubles. It is therefore graded in tiers, against the exact result E, with L the library's output, M the largest absolute input ordinate, P a perimeter and n the number of vertices of both:

  • The rounding floor is δ = ulp(M)/√2, the most that rounding every output vertex to the nearest double can move it. Within it, the output is as good as a double output can be.
  • The library's budget δlib comes from the library's own documentation, recorded in its adapter manifest: a multiple of M, of ulp(M), a grid step, or an absolute distance. A library that documents none is graded in tiers 1, 2 and 4-6 only. GEOS is graded against its loosest documented fallback. Values that could not be checked against a library's source or documentation are marked uncertain in the manifest.
  • In tiers 2 and 3, exact components and holes thinner than δ may vanish or collapse, as may parts of the exact boundary within 2δ of another part of it; the library-to-exact distance and the area bound still apply in full.
  • The topological tier is checked first: invalid output (its point set measured by the even-odd rule), or a missing or extra component or hole that is not thinner than δ.

Only tiers 4-6 count as failures. Rates on this site are always per capability: failures out of the answers graded (correct, wrong, error or convention). Answers outside a library's contract, answers it does not report and cases where the engine abstains are listed, never counted.

Fairness rules

  1. A library is judged only on what it promises. Its adapter manifest records which fields it supports, which are derived from other calls, which it does not offer, its precision model and budget, and its coordinate range. Input outside the contract (coordinates beyond Clipper2's range, lines given to a polygon-only clipper) is unsupported, never wrong.
  2. Library defaults. Every option that departs from a library's defaults is listed in its manifest and on its page.
  3. Output is written exactly. Adapters write output coordinates themselves, in shortest round-trip form, never through a library's text writer with a fixed number of decimals.
  4. Adapters must pass the parse-echo canary (DESIGN §4.1): an adapter that cannot read the input doubles exactly says nothing about its library. Where a run includes the canary, its result is shown on the library's row and page.
  5. A fault is counted once (derived fields), and convention-dependent answers are shown separately.
  6. No single ranking. Libraries differ in what they offer and promise; the scoreboard lists them alphabetically, per capability, with no total.
  7. No automated disagreement is presented as a confirmed bug: see triage.
  8. Maintainers are notified before their library's row is published (geotruth site --preview marks every page of a build as unpublished, for that purpose).
  9. Everything is cited: the library version and commit, the adapter commit and manifest hash, the toolchain, the corpus, the exact answers and the engine version.

Triage

Failures are grouped into clusters: one library, one corpus family, one signature (which DE-9IM entries differ, which predicates are wrong, which overlay tier). Each cluster has a triage status from the registry $registry:

  • unreviewed: found by the harness, not yet looked at by a person;
  • confirmed: a wrong answer within the library's documented contract;
  • reported: confirmed and reported upstream;
  • fixed: fixed upstream;
  • by-design: documented or intended behaviour, not reported as a bug.

A cluster takes the status of the registry entries that name its library, list its family (or no family) and list a field of its capability (or no field). Such a match names a candidate explanation; the cluster page shows the entry's signature next to the cluster's so the reader can judge it. A cluster that matches no entry is unreviewed. The registry's leads (documented candidates without a findings directory, registered by their signature only) are listed on the findings page but never matched automatically. Before a finding is called a bug it is reproduced on the library's latest development code, minimised, checked by an independent skeptic and searched for in the upstream tracker.

The corpus

The cases ($corpus) are deliberately adversarial: each one is built around a degeneracy, either exact (on an integer lattice, so points on edges and shared edges are exact) or at the level of a few ulps (a vertex a few ulps off an edge, a polygon rotated in floating point). In the line, point, collection and empty families about one case in ten is scaled by 2±500 to 2±900, which puts its coordinates between about 1e±150 and 1e±270. The core tier, used for the scoreboard, is a stratified sample of 200 cases per family; the full tier holds every generated case; the curated tier holds the minimal case of every triaged finding. Cases are immutable and dedicated to the public domain (CC0), so any library can copy them into its own tests.

Because the cases are chosen to be hard, a rate on this site is not a real-world failure rate. It says how a library handles inputs at the edge of what floating-point geometry can decide.

Reading the figures

Each example on a failure page has a figure of the whole case and, when the discrepancy is much smaller than the case, a figure zoomed to it; overlay examples add the exact result (filled, solid edges) against the library's output (dashed edges) in the same window. Operand A is drawn with solid edges and round vertex marks, B with dashed edges and square marks. The window, the clipping and every mark position are computed in exact arithmetic, so a window a few ulps wide at coordinates of 1e300 is drawn correctly. The numbered vertices are listed under the figure with their exact coordinates: a double as its shortest round-trip decimal and its exact binary (hexadecimal) value, any other rational as a fraction.

The zoomed window is chosen by the first rule that applies, and its caption says which:

  • overlay: where the library's output is farthest from the exact result, or the exact result farthest from the output (exact distances over vertices and edge midpoints); for invalid output, its first exact defect;
  • relate: the cell of the exact arrangement that realises an entry the library misses (or, when the closest approach between A and B lies inside that cell's window and is much smaller, that closest approach), or the closest approach between A and B when the library reports an entry the exact matrix lacks;
  • validity: the exact defect of an operand the library calls valid, or the closest approach between non-adjacent parts of an operand it calls invalid;
  • otherwise: the closest approach between A and B. This last rule is a heuristic (the corpus puts one near-degenerate spot in each case), and the caption says so.

Reproducing a result

Every example lists the commands that print the exact answer and the library's own answer. From a checkout of the repository:

pip install -e '.[dev]'
export GEOTRUTH_BUILD_DIR=~/.cache/geotruth     # where library builds live
adapters/<dir>/build.sh                          # build a library's adapter
geotruth run --lib <target> --tier core           # the library's answers
geotruth score --lib <target> --tier core         # graded against the exact answers
geotruth site --scores results --out site/_build  # this site

The file formats are JSON Schemas in $schemas.

Adding an adapter

  1. Create adapters/<name>/ with a run command that takes a JSON-lines file of cases (case.v2) and prints one result line per case (result.v2). Isolate every operation: a crash, a hang or a memory failure must fail that operation only.
  2. Write output coordinates yourself, in shortest round-trip form, and report a field the library does not offer as null, and input outside its contract as "unsupported".
  3. Write the manifest adapter.toml ($adapters_readme): supported, derived and unsupported fields; the precision model and the budget δlib, with the documentation it comes from; the coordinate range; every option that departs from the library's defaults; the version command and the build recipe under $$GEOTRUTH_BUILD_DIR. Mark anything you could not check as uncertain.
  4. Build it, then geotruth run, geotruth score and geotruth site. The parse-echo canary must pass, and the engine control must still score 100%. The tests in tests/harness check the manifest.

Limits

  • The corpus is adversarial; its rates are not real-world failure rates.
  • Buffer, offset and simplification, and geodesic, curved and 3-D geometry, are out of scope.
  • The engine abstains on cases over its budget; those cases grade no library.
  • Where the figures fall back on the closest-approach heuristic, the zoomed window is the likeliest place of the discrepancy, not a proven one; the exact answers themselves never depend on it.
